# 每日 AI 新闻助手 Agent：面试讲解与问答

本文以当前代码为依据，和[项目复盘](项目复盘.md)配套。讲稿时长按正常语速估计，应练习后调整；不要把测试替身称为真实模型，不要把单次受控运行称为长期生产运行。

## 一、约 2 分钟项目介绍

我做的是一个本机运行的每日 AI 新闻助手，解决 AI 新闻来源分散、阅读成本高、内容不一定符合个人关注方向的问题。用户填写身份，设置话题、关键词和排除词后，可以手动生成简报，也可以配置每日执行。简报保留原始来源和链接，支持历史查询，以及向已验证邮箱发送。

前端是 Vue，后端是 FastAPI，MySQL 保存偏好、任务、简报和投递状态。核心使用 LangGraph 实现 Function Calling 循环：把任务和工具 Schema 提供给模型，由模型返回工具名称与参数；程序校验并执行，再把结果带着对应 call_id 返回模型。模型可以继续调用、重复调用，也可以结束。代码没有写死先拉 RSS、再搜索、再读原文的步骤。

我比较重视自主性和安全边界的验证。统一注册了五个本地工具和三个新闻工具，用 Mock 模型返回不同 Tool Calls，证明同一执行器会产生不同轨迹；同时完成了真实模型获取新闻、保存简报和邮箱收件验证。新闻来源字段由后端依据候选 ID 填充，不接受模型随意编造链接。

工程上还处理了重复任务、推送失败与超时的不确定性，并加入跨任务累计 Token 预算。邮件先保存再发送，投递状态和生成状态分开。当前范围是单用户 MVP，搜索只覆盖 RSS 候选，bash 只支持受限 JSON 校验命令；没有宣称全网覆盖、多租户或生产级高可用。这个项目让我理解了，Agent 自主决策需要执行器、证据校验和可测试的边界来支撑。

证据入口：[runner.py](../backend/app/agent/runner.py)、[registry.py](../backend/app/tools/registry.py)、[自主性测试](../backend/tests/agent/test_runner.py)、[真实验收记录](完整验收报告.md)。

## 二、约 5 分钟技术讲解

我会沿一次真实任务说明这个项目。用户先在 Vue 页面保存身份和订阅，包括话题、关键词、排除词、时间、时区及本人邮箱。身份和偏好是两个 API 请求，前端会显示部分保存失败。邮箱需要发送测试邮件并由本人确认收件，改地址会清除验证。模型不接触 SMTP 密码，也不决定接收目标。

手动入口和 APScheduler 每日入口最终都进入 TaskCoordinator。后端先锁用户记录，检查活动任务和同日结果，再保存 queued 任务及配置快照。幂等键和数据库条件更新防止多次点击、手动与调度竞争产生重复执行。后台领取后改成 running，每个任务创建独立工作目录和候选上下文。这里用的是进程内后台任务加数据库恢复，不是分布式消息队列。

AgentRunner 用 LangGraph 建立两个核心节点：decide 和 execute_tools。初始化时把统一注册表产生的八个工具 Schema 通过 bind_tools 交给模型，tool_choice 为 auto。decide 读取模型的 tool_calls，没有调用时取最终回答；有调用就交给执行节点。工具执行器用 Pydantic 校验参数、检查权限并返回结构化结果。结果以匹配 call_id 的 ToolMessage 加到消息历史，再回到模型。模型根据观察自行决定接下来做什么。同一响应中的多个工具当前串行执行，包含写文件或 bash 的多调用批次会整体拒绝。

因此自主性不是来自用了 LangGraph 这个名字，而是工具执行的数据来源确实是模型响应。测试用不同 Mock 响应驱动同一执行器，断言不同轨迹、重复调用和模型主动结束；还校验每个 ToolMessage 的 ID。真实验收也保留了模型决策摘要和执行轨迹，不过单次真实轨迹本身不能替代契约测试。

工具分成两组。五个本地工具是列目录、读文件、搜索内容、写草稿和 bash，它们都注册给模型。读和搜索仅限任务材料目录，写只能写 drafts；路径检查拒绝越界、链接和敏感文件。bash 名称保留，但能力被限制为固定 Python JSON 校验命令，使用 shell=False、stdin 快照和超时，不是任意 Shell，也没有完成通用低权限操作系统沙箱。

新闻组是 fetch_rss、search_news、fetch_article。模型只能传配置来源 ID 或候选文章 ID，不能随意构造网址。search_news 搜索当前任务已取得的 RSS 候选，不是全网搜索。网络层限制来源域名，解析后校验公网地址并固定连接 IP，逐跳检查重定向，同时保留 TLS 校验，降低 SSRF 和 DNS 再解析风险。原文做有界提取，允许重复读取分块。

用户偏好通过任务提示影响模型选源、搜索和最终筛选。话题是方向，关键词提高优先级，不强制每条命中。模型只输出候选 article_id、摘要和相关性理由；后端从真实材料补齐标题、来源、链接和发布时间。未知 ID、无材料、非法 JSON 或排除词命中会拒绝保存。这样能约束来源和格式，但不能保证模型每句话都准确；没有做推荐算法训练或准确率评测。

通过校验后，简报和任务、工具轨迹、邮件待发送记录一起落库，之后独立投递。发送前重新确认邮箱仍被保存、验证并启用，防止向变更后的旧目标投递。SMTP 接受仅记 submitted。临时错误有限退避，DATA 阶段超时可能已经发出，因此记 unknown，不盲目重试。这是减少重复风险的选择，不能宣称跨数据库和 SMTP 精确一次送达。

项目还实现了共享的 100 万 Token 账本。每次模型 HTTP 请求前在数据库原子预留额度，收到 usage 后结算；超时或未知用量保留占额，数据库异常时拒绝调用。估算使用请求字节与输出上限，是保守控制，不是精确分词或第三方账单保证。

验证分为工具、Agent 决策、协议、业务事务、前端和显式开启的真实服务测试。历史完整测试为后端 166 通过、1 项 Windows 符号链接权限跳过，前端 41 通过；真实链路生成了 4 条新闻，SMTP 一次提交，用户确认收到。当前每日调度停用，还没有长期运行、负载和公网安全验收。下一步应先补来源质量评测、增量与新鲜度策略；如果要公网部署，再补认证、租户隔离和可靠队列，而不是直接放大当前本机实现。

各段对应源码：[tasks](../backend/app/application/tasks.py)、[runner](../backend/app/agent/runner.py)、[tools](../backend/app/tools/registry.py)、[news](../backend/app/news/service.py)、[briefs](../backend/app/application/briefs.py)、[deliveries](../backend/app/application/deliveries.py)、[budget](../backend/app/application/budget.py)。

## 三、10 个可能的面试问题与回答

### 1. 这是真 Agent，还是固定工作流套了 LLM？

外层任务排队、保存和发送是普通后端流程，任务内部的工具决策是模型驱动。`AgentRunner` 绑定工具 Schema，`decide` 读取模型 `tool_calls`，执行后通过 ToolMessage 再交给模型，直到它不再请求工具。业务代码没有硬编码新闻工具顺序。安全预算或轮数上限会强制中断，这与模型正常自主结束要分开。

证据：[runner.py](../backend/app/agent/runner.py)，[test_runner.py](../backend/tests/agent/test_runner.py) 中不同决策不同轨迹、重复工具、零工具结束三个测试。

### 2. 模型自己决定顺序，代码怎么确保调用合法？

模型提出动作不等于获得权限。ToolRegistry 只接受已注册名称，用 Pydantic Schema 拒绝非法字段与参数，再由具体工具检查路径、域名、资源等权限，最后返回统一 ToolResult。未知工具或参数错误会回传模型，模型可以修正。写文件/bash 混入多调用批次时整批拒绝，避免有副作用的组合执行。

证据：[registry.py](../backend/app/tools/registry.py)、[schemas.py](../backend/app/tools/schemas.py)、`test_side_effecting_multi_tool_batch_is_rejected_without_writing`。

### 3. 用 Mock 模型如何证明自主性，会不会只是另一种固定流程？

Mock 本身当然是脚本，目的不是验证真实模型智能，而是验证执行器的数据依赖。给同一个 AgentRunner 不同的模型响应，断言工具轨迹随响应变化；再测试重复、直接结束、出错后继续以及匹配 call_id 的结果回传。如果执行器写死流程，这些测试应失败。真实模型路径另做兼容性和业务可行性验证，两者证据不同。

证据：[test_runner.py](../backend/tests/agent/test_runner.py)、[test_model_protocols.py](../backend/tests/agent/test_model_protocols.py)、[完整验收报告](完整验收报告.md)。

### 4. 模型不能联网，新闻从哪里来？怎么防止编造？

联网由实际 RSS 和网页工具完成，模型只决定是否调用。候选保留 source、URL、日期和材料，模型最终引用 article_id。`_hydrate_items` 验证 ID 属于本任务证据、来源启用、URL 合法且有节选，再由后端填来源字段。未知 ID 会拒绝保存。但这不能证明每句概括都正确，事实一致性还需要质量评测。search_news 只是本地候选检索，不是全网搜索。

证据：[service.py](../backend/app/news/service.py)、[briefs.py](../backend/app/application/briefs.py) `_hydrate_items`、[test_briefs.py](../backend/tests/application/test_briefs.py)。

### 5. 用户偏好真的有作用，还是只存在数据库？

执行任务时将偏好做快照，`_build_task` 把话题、关键词、排除词和身份语境写进实际模型输入。模型可据此改变选源、检索和摘要，输出相关性理由。排除词另有代码字面检查，命中就拒绝整份简报。测试替身在不同上下文下产生不同调用和结果，证明配置传递和处理链路有效；没有足够标注数据证明真实模型匹配准确率。

证据：[briefs.py](../backend/app/application/briefs.py) `_build_task`/`_hydrate_items`，`test_model_decisions_drive_different_brief_traces_and_persist_evidence`。

### 6. 文件工具和 bash 有什么安全风险？

风险包括目录穿越、链接越权、读取秘密、命令注入和资源耗尽。当前只允许任务工作区的有限目录和类型，拒绝绝对路径、上级路径、ADS、链接等；写只能落 drafts。bash 只运行固定 Python JSON 校验器，先安全读取文件再通过 stdin 传子进程，禁用 shell，设输入/输出、深度和超时限制。没有支持任意命令，也没有完成通用 Windows 低权限沙箱和同用户竞态隔离。

证据：[filesystem.py](../backend/app/tools/filesystem.py)、[commands.py](../backend/app/tools/commands.py) 及 [tools 测试](../backend/tests/tools/)。

### 7. 怎么处理重复点击、重复调度和重复邮件？

排队时锁用户记录，检查活动任务及同日结果，再配合唯一幂等键；领取任务使用条件状态更新。投递另有记录、唯一约束、领取锁和次数限制。SMTP DATA 超时属于“可能已经发出”，标记 unknown 而不盲重发。真实 MySQL 8 路竞争验证了唯一领取，但这不是高并发性能测试，也不能证明跨系统 exactly-once。

证据：[tasks.py](../backend/app/application/tasks.py)、[deliveries.py](../backend/app/application/deliveries.py)、[smtp.py](../backend/app/delivery/smtp.py)、[实库测试](../backend/tests/integration/test_mysql_acceptance.py)。

### 8. 服务器重启后任务会怎样？LangGraph 能断点恢复吗？

任务记录持久化在 MySQL，当天中断的任务可以重排队，新尝试使用新上下文并保留旧轨迹；跨日或调度停用等情形会明确处理。未完成 LangGraph Checkpointer，所以不能在中间节点无损续跑，可能重复模型/只读工具成本。中断投递的 sending 转 unknown，优先避免重复发信。当前还有单 worker、数据库可用和恢复流程的运行前提。

证据：[tasks.py](../backend/app/application/tasks.py) `recover_interrupted_today`、[test_tasks.py](../backend/tests/application/test_tasks.py)、[runner.py](../backend/app/agent/runner.py)。

### 9. 怎么控制模型费用？超时怎么算？

项目级预算放在模型 HTTP 边界，不仅在任务结束时统计。请求前数据库原子预留，收到 usage 后结算；超时和缺失用量保留占额，重启也不退回。额度不足或数据库不可用时拒绝新请求，Agent 记 limited/failed，不保存假成功简报。历史无法核对部分留有用户同意的安全预留。它是本地保守控制，不能完全约束供应商虚报或额外计费。

证据：[budget_client.py](../backend/app/agent/budget_client.py)、[budget.py](../backend/app/application/budget.py)、[test_budget.py](../backend/tests/test_budget.py)、[累计预算控制](累计预算控制.md)。

### 10. 当前最大的不足是什么，下一步怎么做？

产品侧 RSS 覆盖和新鲜度有限，搜索不是全网，语义去重和摘要质量没有量化；工程侧是本机单用户、单 worker、没有精确图恢复和通用 OS 沙箱。先用固定新闻样本评估相关性、遗漏和事实一致性，再做来源扩展和真正的增量读取。如果需要公网化，应先补身份认证、租户隔离、队列与运维，而不是用现有并发正确性测试宣称生产可扩展。

证据：[项目复盘的状态与取舍](项目复盘.md)、[完整验收限制](完整验收报告.md)、[新闻仓储](../backend/app/news/repository.py)。

## 四、最值得展示的 3 个 Agent 技术亮点

| 亮点 | 展示方式 | 表述边界 |
| --- | --- | --- |
| 可证实的模型自主工具循环 | 读 `bind_tools → pending_calls → ToolMessage`，运行不同 Mock 路径/重复/停止测试，再看已有真实轨迹 | 展示可观察调用，不展示或伪造模型思维链；工具批次实际串行 |
| 自主决策与硬权限分离 | 展示统一 Schema、路径/命令限制和新闻来源 ID 约束；用拒绝越权测试说明模型没有提升权限能力 | 固定 JSON 命令不等于通用 Shell 沙箱；外部文本仍有提示注入风险 |
| 带证据与成本约束的任务闭环 | 展示真实候选 ID 校验、来源填充、落库与投递分离，再看预算预留/结算及 unknown 保留 | 来源可追溯不等于摘要绝对正确；SMTP submitted 不等于自动送达确认 |

## 五、演示与自查清单

一次无需新付费调用的演示可以这样安排：

1. 打开当前简报和历史，说明真实来源、原文节选、日期以及覆盖不足提示。
2. 在后端运行只读轨迹诊断，逐一对应模型请求的工具、call_id、执行结果和最终 brief_id。
3. 运行 Mock 决策测试，展示相同执行器在不同模型响应下走不同路径。
4. 对照代码讲清新闻校验和邮件状态，展示已有 submitted 及用户确认收件证据；不要为演示重复发送。
5. 展示预算摘要，说明已确认、待核对和可用额度不同，并说明没有负载容量或准确率指标。

```powershell
# 从项目 backend 目录执行，均不调用真实模型或发邮件
uv run --locked python -m app.diagnostics acceptance-b979912c-6efd-4e31-8df7-e57cd8872e29
uv run --locked pytest tests/agent/test_runner.py -q
uv run --locked python -m app.budget status
```

如需要从保存偏好开始新增真实演示，按[部署与演示](部署与演示.md)操作，先核对额度和已验证目标；保持订阅关闭可以演示生成但不发送新闻。不要在讲解时临时初始化或重置正式预算。新的模型响应、新闻数量与耗时不保证复现历史值。
